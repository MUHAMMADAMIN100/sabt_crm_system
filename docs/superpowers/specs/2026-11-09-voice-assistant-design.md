# Голосовой помощник в Telegram-боте — устройство

Дата: 09.11.2026. Решения владельца — из разговора 09.11; мои решения помечены «(моё)».

## Зачем

Голосовые в боте перестали работать: Gemini ответил 402 (кончился предоплаченный
баланс), запасного пути для разбора смысла не было. Владелец хочет больше, чем
починку: говорить боту что угодно — «смени статус задачи на готово», «начни
работу», «какие задачи у Сабрины?» — и бот **точно и без ошибок** делает это в
CRM или отвечает прямо в чате.

## Цели

- Голосом и текстом — команды CRM от имени сотрудника и вопросы о данных CRM.
- Ровно те же права, проверки и последствия, что на сайте (уведомления,
  журналы, живое обновление экранов).
- Русский и таджикский на входе, ответ по-русски, текстом в чате.
- Простые действия — сразу, с кнопкой «↩ Отменить»; рискованные (удаление,
  поручение другому, деньги, массовые) — после подтверждения.
- Поставщик ИИ — OpenAI; Groq и Gemini — запасные, отказ одного не роняет бот.
- Выкладка частями: 1) распознавание + задачи + вопросы + рабочий день;
  2) клиенты и лиды; 3) СММ и финансы.

## Не цели

- Голосовой ответ (озвучка) — нет, ответ текстом.
- Ответы клиентам в «Директ» голосом — нет (не просили, высокий риск).
- Новые возможности CRM: бот умеет только то, что уже умеет сайт.
- ИИ-помощник на сайте (`modules/ai-assistant`) — не трогаем в этой работе.

## Анти-цели (провал, даже если «работает»)

- Бот сделал то, что человеку нельзя на сайте, или показал чужие данные.
- Бот угадал не ту задачу/человека и молча изменил её.
- Тишина или «что-то пошло не так» без понятной причины.
- Долгое ожидание без признаков жизни (показываем «печатает…»).

## Устройство

```
Telegram ──webhook (secret_token)──▶ TelegramController
   голос/текст/ответ на карточку        │
                                        ▼
                         VoiceAssistantService (modules/voice-assistant)
   1. сотрудник по chat id (активен, не заблокирован)
   2. снимок контекста через API от его имени: мои открытые задачи,
      сотрудники, проекты — с короткими метками T1/E1/P1
   3. речь → текст: OpenAI gpt-4o-transcribe (подсказка — имена),
      запасные Groq whisper-large-v3, Gemini
   4. LLM с инструментами (формат OpenAI tools): OpenAI → Groq → Gemini;
      до 5 шагов: чтение — свободно, запись — через исполнителя
   5. исполнитель: каждое действие = вызов /api/... с JWT этого сотрудника
      (2 минуты, только внутри процесса) → те же guard'ы, DTO, сервисы
   6. ответ: итог действий + «↩ Отменить» / «Подтвердить» / выбор кнопками
```

Ключевое решение (моё): **действия идут через собственный HTTP API от имени
сотрудника**, а не прямыми вызовами сервисов. Разбор показал, что часть проверок
живёт только в контроллерах: `@RequirePerm` (PermissionsGuard), DTO с
`forbidNonWhitelisted`, `FinanceAccessGuard`, журнал финансов
(`FinanceActivityInterceptor`), сброс кэша (`ClearCacheOnWriteInterceptor`).
Вызов API воспроизводит всё это без копирования логики.

Исключения, где сайт ограничивает на фронтенде, а сервер — нет (бот повторяет
фронтенд):
- обычный сотрудник видит задачи через `/tasks/my`, общий `GET /tasks` — только
  руководство и менеджеры продаж (`TasksPage.tsx:87`);
- менеджеру продаж владелец лида — всегда он сам.

### Инструменты (волна 1)

Чтение: `find_tasks` (мои / сотрудника / по проекту / просроченные / по
тексту, со статусом и сроком), `task_details`, `find_employees`,
`list_projects` (счёт и список, как на сайте), `shift_status`
(`/work-shifts/my`, `my-month`), `team_shift_status` (руководство).

Запись:
| инструмент | API | риск |
|---|---|---|
| `set_task_status` | PATCH /tasks/:id {status}; для цепочки исполнителей — POST my-part-done | сразу |
| `create_task` | POST /tasks (себе — сразу; другому — подтверждение) | сразу/подтв. |
| `update_task` (срок, название) | PATCH /tasks/:id | сразу |
| `comment_task` | POST /tasks/:id/comments | сразу |
| `approve_task` / `return_task` | POST approve / return | сразу |
| `delete_task` | DELETE /tasks/:id {reason} | подтверждение |
| `shift_start` / `shift_pause{kind}` / `shift_stop` | POST /work-shifts/* | сразу |
| `shift_notice` (приду позже) / `shift_edit_request` (забыл отметить) | POST notices / edit-request | сразу |
| `set_absence` (руководство) | POST /work-shifts/absence | подтверждение |

Отмена: перед записью снимаем прежнее состояние (статус, срок, название) и
запоминаем обратную операцию на 60 минут. Создание → удаление с причиной
«Отменено в Telegram». Отменить нельзя — кнопку не показываем.

Уточнение: `ask_choice` — бот показывает варианты кнопками; выбор
перезапускает разбор той же фразы с выбранным вариантом.

Короткая память разговора (моё): 4 последних обмена за 20 минут —
«и поставь ей срок на пятницу» понимается. Ответ голосом/текстом на карточку
задачи в боте привязывает команду к этой задаче.

### Волны 2–3 (те же механизмы, новые инструменты)

Клиенты: создать лид (владелец — сам МП), сменить статус / этап онбординга,
«заметка» → `nextStep` / `repeatCallAt` / `nextContactAt`, поиск, KPI,
«кто не оплатил» (`/smm-payments/calendar`).
СММ: сторис (`POST /stories`, считать от нормы дня), карточки
контент-плана (`smart-item` / `my-work`), перенос съёмки, назначение
видеографа (админ/основатель), отчёт за день.
Финансы (только `finance.manage`): операция (доход/расход/перевод),
оплата клиента (план → receive, иначе payNow), балансы, итоги месяца,
просрочки; отмена — отмена операции.

## Безопасность

- Webhook: `secret_token` = производная от токена бота (моё — без новой
  переменной); при старте в production бот сам переустанавливает webhook с
  секретом; запросы без верного заголовка отклоняются.
- JWT для внутренних вызовов живёт 2 минуты, наружу не уходит.
- Данные CRM в подсказке ИИ помечены как данные, не команды; рискованное — только
  с подтверждением; права всё равно проверяет API.
- Лимит: 40 команд за 10 минут на человека (моё) — защита от счёта за ИИ.

## Ошибки

- Отказ поставщика (оплата/ключ/лимит/сбой) — тихо следующий поставщик.
- Все отказали — понятная причина («кончился баланс OpenAI…»).
- Ответ API 400/403 — текст ошибки сайта человеку как есть
  («Загрузите результат…» → кнопка «📎 Приложить результат»).

## Проверка

- Модульные тесты: метки, исполнитель, отмена, подтверждение, секрет webhook,
  классификация ошибок ИИ.
- Сценарии на настоящих голосовых (OGG/Opus, как в Telegram) против локального
  бэкенда и локальной базы, Telegram подменён; проверка — по состоянию базы.
- Таджикский — 2–3 голосовых владельца.
- После выкладки — живой бот в чате владельца; тестовые записи удаляются.

## Что оставлено исполнителю

Тексты ответов, точные описания инструментов для ИИ, формат списков в чате,
пороги нечёткого поиска.
